## Device and replay

- WorkStore issues an owner/profile-scoped one-use pairing code with a five-minute lifetime. A successful enrollment atomically replaces the code digest with a digest of a separate 30-day credential. The database stores digests and device metadata. Revocation and expiry remove device authority on the next check. The restore path clears old pending and active credentials from the restored copy.
- The transport-independent feed authenticates each snapshot and replay. It projects conversation-linked tasks from the existing WorkStore and replays up to 128 committed events after a scoped cursor. A missing, foreign or stale cursor requires a fresh snapshot. Events expose task ID, version, status and time. Snapshots omit session identities, source destinations, private constraints and artifacts.
- The pinned DSH Web connection maps its browser credential to a shared owner Peer. Exact Fetch routes require that owner Peer. The existing inbox also binds an approval to an exact client, device and session. These boundaries determine the separate mobile admission path and the explicit approval handoff. [Pinned host evidence](host-compatibility.md) · [Native access contract](https://github.com/deepseek-ai/deepseek-harness/blob/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/packages/api/remote-access/README.md)

## Mobile HTTP and Web

Commit `d833b4a21a49c56641ae1cda2a021d87b4cd76b6` wires the ledger and feed into an opt-in loopback HTTP listener. The operator's dedicated HTTPS origin terminates TLS at a reverse proxy. The upstream validates Host, Origin and Fetch Metadata, and pairing sets an independent secure, HttpOnly, SameSite=Strict cookie. The native local owner uses Today to issue a pairing code and revoke devices.

The separate responsive page reads scoped snapshots and follows the SSE stream. An out-of-window cursor requests a fresh snapshot. The stream rechecks the device on each poll and closes on revocation. The mobile listener exposes its own assets and pairing, snapshot, event and assigned approval routes. [Setup](../../README.md#opt-in-to-the-mobile-work-view)

## Exact mobile reviews

Commit `9373a93dd183b9a1ecba14adc816e4134b3845dc` adds versioned handoff to one enrolled device and recall by the original owner client. WorkStore v15 keeps the original approval binding and the assigned responder separately. The phone submits the expected version, digest and approve or deny decision to the existing exact-action gate. ## Recovery after a stalled Chrome handshake

[Issue #111](https://github.com/MosBot-AI/dsh-personal-agent/issues/111) follows a [main CI failure at `356803a`](https://github.com/MosBot-AI/dsh-personal-agent/actions/runs/43387484823/attempts/1). The browser reported no exit or signal and did not answer `Browser.getVersion` within 10,003 ms. The unchanged [second run](https://github.com/MosBot-AI/dsh-personal-agent/actions/runs/43387484823/attempts/2) passed.

When the initial ten-second handshake expires, the fixture records the timeout and waits up to four seconds for the first process and its pipes to close, escalating from SIGTERM to SIGKILL after two seconds. Only after cleanup succeeds does it launch one replacement with a fresh disposable profile and an eight-second handshake deadline. This adds at most twelve seconds to the handshake budget. Pipe closure, process exit, an explicit rejection or a failure after handshake still surfaces directly. Ordinary DevTools commands keep their eight-second deadline. Mobile product assertions remain unchanged.

Eight deterministic fixture cases passed, including waiting for close after exit, a persistent stall with no third launch, and failed cleanup with no replacement. All five native mobile cases passed with Chromium 154.0.8037.92. In a separate run, a launcher held the first process without a DevTools reply and used real Chromium only for the replacement. The existing pairing, approval, visibility, reconnect and revocation case passed. The run recorded exactly two launches and retained the first handshake timeout in its output.
