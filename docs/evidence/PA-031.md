[简体中文](PA-031-zh.md)

[PA-031](https://github.com/MosBot-AI/dsh-personal-agent/issues/25) · Plan `2026-11-07-r7` · Implementation through `b7a9ce7dbb3bc1680d42509793e3eedcdfb857b0`.

## Implemented boundary

- In Today, the authenticated owner authorizes a task attempt for an exact macOS application or configured browser target. An OS-backed per-user reservation serializes desktop workflows across local profiles. The browser path binds its profile lease to a freshly isolated, exact native tab. Each model action rechecks the current lease and native target. Starting or continuing requires foreground authorization.
- The macOS path uses DSH Computer Use. It probes the session and Accessibility before model admission, then uses the provider's application consent and AX snapshots. The browser path uses DSH's Session-owned MCP runtime with pinned headless Chrome DevTools. The provider applies a configured network allowlist, and the task narrows tool calls to its own origin and tab. Structured page IDs route actions, and a bounded top-level observation supplies the only accepted element IDs.
- Takeover fences new input immediately and preserves the running operation's drain status. The Worker parks and releases its compute slot after teardown. Continuation creates a fresh lease and requires fresh observation. Browser Session teardown discards the isolated context.
- The dedicated deployment admits only its lease-gated model tool. Native shell and program execution stay disabled at this boundary. OS-level sandboxing requires a separately enforced backend.

## Historical Linux native readiness slice

The earlier readiness-only candidate recognized the already mounted `cua-driver-native` provider on Linux and ran only its pinned read-only permission probe inside the existing desktop lease. It does **not** enable application discovery, screenshots, input, model admission or foreground retries. Unknown OS lock state is reported as `session_state_unavailable`; unsupported Wayland as `unsupported_desktop`. Missing X11/AT-SPI/input capability remains a permission wait. Direct raw provider tools remain blocked by the deployment guard. Provider replacement, malformed/error responses and lease loss fail closed. Native D-Bus addresses are not returned to the Worker.

Contract audit: DSH commit `fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159`, [native provider](https://github.com/deepseek-ai/deepseek-harness/tree/fcc0ad462172522aaf5c93a7b2e01f6b9f0b0159/packages/experimental/computer-use-cua-driver-native), pins `@trycua/cua-driver@0.28.0`. SDK source tag `cua-driver-rs-v0.28.0` resolves to `1b50c02e2d34734f64d2d22f54eb76cc97b4a663` in [trycua/cua](https://github.com/trycua/cua/tree/1b50c02e2d34734f64d2d22f54eb76cc97b4a663/libs/cua-driver/rust). Its Linux `platform-linux/src/tools/impl_.rs` defines strict empty arguments for `check_permissions`, returning X11, Wayland, AT-SPI and input capability booleans. The macOS-style `{prompt:false}` is not the Linux contract. `cua-driver-contract/src/outputs.rs` explicitly says `desktop_unlocked` is a capture-scope grant, not an OS lock-screen probe. `platform-linux/src/input/delivery.rs` warns Wayland background input can target compositor focus. Neither signal authorizes safe exact-window input.

Remaining implementation: trusted OS session-lock observation, Linux XDG application identity (not a macOS bundle-ID assumption), exact live PID/window binding, fresh per-window tokens, and background-only action verification. Physical lock/sleep/wake and native input acceptance remain unverified. The readiness-only candidate used reverse-DNS application identifiers and preserved the authority boundary around process and window identifiers. No permission, power or security settings changed, no model was invoked, and no live native action was attempted.

Validation is keyless with deterministic capability results, not real native-device acceptance. Independent review found no blocking safety defect in the readiness-only boundary and requested in-flight takeover and host admission regression coverage, both added. The pre-change baseline type check/build passed, but one existing schedule recovery assertion failed in the full suite (328/329); a standalone rerun passed all six schedule tests. This baseline fluctuation is not attributed to the Linux change. The user knowledge-base path was unavailable; source claims above were checked against pinned upstream code.

## Explicit Linux target configuration

The configuration change for [Issue #77](https://github.com/MosBot-AI/dsh-personal-agent/issues/77) integrates the reviewed scope of [#74](https://github.com/MosBot-AI/dsh-personal-agent/pull/74) and [#78](https://github.com/MosBot-AI/dsh-personal-agent/pull/78). `linuxApplications` accepts exact XDG IDs separately from the existing macOS `applications` list. Durable authority uses a distinct `linux:` namespace. Switching the provider cannot reinterpret prior macOS task grants. No native application is launched or discovered merely by configuring an ID.

The configured Linux target carries `unavailableReason=linux_binding_unavailable`. Today shows localized unavailable text and disables launch; the server independently rejects direct launch before context, lease and Worker setup. This supersedes the earlier readiness-only launch path: Linux target configuration does not spend a Worker or call a provider to rediscover a known missing security boundary. The final runtime removes the unused readiness probe and its two dedicated wait reasons. Existing macOS targets never select the Linux provider.

Pinned SDK `platform-linux/src/tools/impl_.rs` associates installed XDG entries to running processes by executable basenames and ambiguity heuristics. Its `bundle_id` is not a trusted application-to-process binding. Official [logind documentation](https://www.freedesktop.org/software/systemd/man/latest/org.freedesktop.login1.html) describes `LockedHint` as state reported by the desktop environment; false alone cannot prove an unlocked session. No discovery, snapshot or input adapter was enabled on those assumptions. Process lifetime/PID reuse protection, exact native window ownership, fresh tokens and trusted session/locker integration remain implementation gates.

Historical stack validation: 35 desktop unit tests, two native-host desktop cases and two bilingual UI cases passed; type check, build, plan, 12 coordination tests and whitespace checks passed. Cross-review found no blocking admission/UI defect. The exact stacked candidate passed 360/361 full-suite tests, with only the previously reproduced #75 schedule race failing. Applying **only the two test-file changes from pending PR #76** temporarily produced 361/361; those changes were then reversed and are not included here. This distinguishes a green combined verification from the exact candidate's remaining baseline failure. Neither original PR had merged at that checkpoint.

The integrated change shares the 16 macOS, 16 Linux and eight browser target limits between runtime configuration and the Today client. The pinned native Web suite accepted authenticated snapshots with 24, 25 and 40 configured targets. The served browser bundle rejected a deliberately injected 41st target. The Linux launch test confirmed that the direct RPC returned `linux_binding_unavailable` without creating Worker input, and that a macOS grant stayed on its original path.
