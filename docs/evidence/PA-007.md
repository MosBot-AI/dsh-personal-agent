## Implemented boundary

- The artifact store seals up to 256 KiB of UTF-8 text, Markdown, or parseable JSON per version. It derives the SHA-256 digest and storage reference, records scoped source references and visibility, and binds each revision to its producing Attempt and generation. Revisions form a linear history. Scoped reads verify persisted content and return detached bytes.
- Worker readiness admits only sealed, exact-attempt artifacts. The executor commits its one-use release proof after native cleanup. The verifier checks actual bytes and required confirmed Effect receipts, receives redacted evidence from a trusted criteria checker, and rechecks the task version and evidence after the checker completes. Completion, verification evidence, and original-destination delivery intents commit in one transaction.
- Outbox `pending` records represent locally generated deliveries. A durable claim precedes provider I/O and binds the exact route and account. Immutable destination, content, dedupe key, and origin remain fixed. The controller serializes sends per task and channel while unrelated work continues. Attachment sends recheck sealed bytes against verification and apply trusted disclosure rules, with separate approval for private artifacts.
- Provider acceptance, delivery, and readback are distinct states. Positive readback advances exact receipts monotonically. Unknown outcomes and ordinary absence stay uncertain. Only a correlated definitive no-send result can permit bounded retry. An open provider operation holds the store writer against graceful close until it settles.
- Schema 003 preserves source-version v1 or v2 data and takes an owner-private backup including committed WAL content before upgrade. A migrated native Attempt awaiting verification without release evidence remains in that state pending recovery.
